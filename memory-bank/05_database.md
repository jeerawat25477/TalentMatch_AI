# 05 — ความเสี่ยงของฐานข้อมูลที่รอแก้ (ตรวจเมื่อ 2026-09-17)

**สถานะ: ยังไม่แก้โดยตั้งใจ** ผู้ใช้ตัดสินใจเลื่อนไปทีหลัง เพราะตอนนี้ไม่มีข้อไหนขวางงานพัฒนา:
ข้อมูลยังเล็ก (21 ผู้สมัคร, ฐานข้อมูล 12 MB) รันบน Docker ในเครื่อง พอร์ต DB ไม่เปิดออกนอก
และ timezone ของ DB เป็น UTC

**ต้องกลับมาอ่านไฟล์นี้เมื่อ:** จะ deploy จริง · จะย้ายไป Supabase · งานใหม่แตะ `schema.sql`
หรือ `app/database.py` · จะรันมากกว่าหนึ่ง replica

ทุกข้อตรวจจากฐานข้อมูลและโค้ดจริง ตัวเลขในวงเล็บคือค่าที่วัดได้ ณ วันที่ตรวจ
แก้ข้อไหนแล้ว ให้ขีดฆ่าหัวข้อ แล้วเขียนวันที่กับ commit ต่อท้าย

## ต้องแก้ก่อน deploy

### 1. Supabase: ตารางอาจถูกอ่านจากภายนอกได้ทั้งหมด
- **อาการ:** Supabase เปิด REST API (Data API) ให้ schema `public` เป็นค่าเริ่มต้น ทุกตารางของเรา
  อยู่ใน `public` และยังไม่เปิด Row Level Security เลย คนที่ได้ anon key (ซึ่งเป็นคีย์สาธารณะ)
  อาจอ่านเรซูเม่ ผลประเมิน และตาราง `users` ได้
- **ทำไมยังไม่ขวาง:** ตอนนี้ใช้ Postgres ใน Docker ไม่มี Data API
- **วิธีแก้:** เปิด RLS ทุกตาราง (ไม่ต้องเขียน policy ก็ได้ เพราะ backend ต่อด้วย role ที่ข้าม RLS)
  หรือปิด Data API ของโปรเจกต์
- **ระวัง:** ตาราง checkpoint ของ LangGraph ก็อยู่ใน `public` และมีข้อความเรซูเม่อยู่ใน state ด้วย

### 2. connection ของ checkpointer ต่อใหม่เองไม่ได้
- **อาการ:** `app/database.py::get_checkpointer` เปิด `Connection.connect(...)` ครั้งเดียวแล้วใช้
  ตลอดอายุแอป ถ้า DB รีสตาร์ต หรือ cloud ตัดการเชื่อมต่อที่ idle ทุกอย่างที่แตะกราฟจะล้มจนกว่า
  จะรีสตาร์ต backend: วิเคราะห์ผู้สมัคร, ตัดสิน HITL, `graph_status`
- **ทำไมยังไม่ขวาง:** DB อยู่ในเครื่อง ไม่มีใครตัดการเชื่อมต่อ
- **วิธีแก้:** ให้ `PostgresSaver` ใช้ `ConnectionPool` (รองรับอยู่แล้ว) หรือเช็ค/ต่อใหม่ก่อนใช้
- **ระวัง:** pool ของตารางแอป (`get_pool`) ฟื้นเองได้อยู่แล้ว มีแค่ตัวนี้ที่ไม่ฟื้น ·
  ต้องรักษา `autocommit=True` ไว้ตามที่ PostgresSaver ต้องการ

### 3. รหัสผ่าน DB เป็นค่าเริ่มต้น
- **อาการ:** `docker-compose.yml` ตั้ง user และรหัสผ่านเป็น `talentmatch/talentmatch`
- **ทำไมยังไม่ขวาง:** ไม่ได้ publish พอร์ต 5432 ออก host
- **วิธีแก้:** ย้ายไปอ่านจาก `.env` และตั้งค่าที่แข็งแรงก่อน deploy

### 4. ชนิดการเชื่อมต่อ Supabase — ต้องทดสอบ ยังไม่ได้ยืนยัน
- **อาการที่อาจเกิด:** `.env.example` ใช้แบบต่อตรง `db.xxxx.supabase.co:5432` ตามที่ทราบ
  แบบต่อตรงอาจใช้ได้แค่ IPv6 (เซิร์ฟเวอร์ที่ไม่มี IPv6 จะต่อไม่ติด) ส่วน transaction pooler
  พอร์ต 6543 อาจพังกับ prepared statement ที่ psycopg ใช้อัตโนมัติ
- **วิธีแก้:** ทดสอบกับโปรเจกต์ Supabase จริงก่อน น่าจะใช้ session pooler ได้ ถ้าจำเป็นต้องใช้
  transaction pooler ให้ตั้ง `prepare_threshold=None`

## จะเป็นปัญหาเมื่อข้อมูลโตหรือระบบเปลี่ยน

### 5. ไม่มีระบบ migration
- **อาการ:** `init_db()` รัน `schema.sql` ทั้งไฟล์ทุกครั้งที่บูต ด้วย `CREATE ... IF NOT EXISTS`
  และ `ADD COLUMN IF NOT EXISTS`
- **ผลกระทบ:** ถ้าแก้ CHECK ของตารางที่มีอยู่แล้ว (เช่นเพิ่มขั้นใน `hiring_stage_stage_check`)
  **DB เดิมจะไม่เปลี่ยนตาม แบบเงียบ ๆ** แล้ว INSERT ค่าใหม่จะล้มตอนรันจริง · ลบหรือเปลี่ยนชนิด
  คอลัมน์ไม่ได้ · หลาย replica แย่งกันรัน DDL ตอนบูต
- **วิธีแก้:** ใช้เครื่องมือ migration (เช่น Alembic หรือไฟล์ SQL มีเลขลำดับ + ตารางจดเวอร์ชัน)
  ก่อนที่ schema จะเปลี่ยนแบบนี้ครั้งแรก · ระหว่างนี้ ถ้าต้องแก้ CHECK ให้เขียน
  `ALTER TABLE ... DROP CONSTRAINT IF EXISTS` แล้ว `ADD CONSTRAINT` ตามแพตเทิร์น `DO $$` ในไฟล์

### 6. `evaluations.candidate_id` ไม่มี index และไม่มี UNIQUE
- **อาการ:** มีแค่ primary key ที่ `id` · ทุกหน้าที่ join ผลประเมินสแกนทั้งตาราง ·
  กฎ "หนึ่งคนหนึ่งผลประเมิน" อยู่แค่ในโค้ด (`runner._persist_evaluation` DELETE แล้ว INSERT)
  ถ้าสองงานชนกันจะได้แถวซ้ำ แล้วหน้าเว็บแสดงผู้สมัครซ้ำ
- **วิธีแก้:** `CREATE UNIQUE INDEX IF NOT EXISTS ... ON evaluations (candidate_id)`
- **ระวัง:** ต้องล้างแถวซ้ำก่อน ไม่งั้นสร้าง UNIQUE ไม่สำเร็จ และจะทำให้ `init_db` ล้มตอนบูต
  (ณ วันที่ตรวจ ยังไม่มีแถวซ้ำ: evaluations 21 แถว = ผู้สมัคร 21 คน)

### 7. `processing_queue.candidate_id` ไม่มี index และแถวที่เสร็จไม่ถูกลบ
- **อาการ:** หน้ารายชื่อ poll ทุก 4 วินาที และค้นคิวรายคนผ่าน LATERAL join · มีแค่ index
  `(status, created_at)` · แถว `done` สะสมตลอดไป
- **วิธีแก้:** index ที่ `(candidate_id, status)` และงานล้างแถว `done` ที่เก่ากว่า N วัน

### 8. ตารางที่โตโดยไม่มีการล้าง
- checkpoint ราว 10 แถวต่อผู้สมัคร (223 แถว / 21 คน, blob เฉลี่ยราว 8 KB ต่อคน)
- `email_intake_log` หนึ่งแถวต่ออีเมลหนึ่งฉบับ
- `processing_queue` แถวที่ทำเสร็จแล้ว
- **ทำไมสำคัญ:** Supabase แผนฟรีมีพื้นที่ 500 MB · ควรมีงานล้างข้อมูลเก่าตามช่วงเวลา
- **ระวัง:** checkpoint ของคนที่รอ HR หรือค้างกลางทางต้องเก็บไว้ ห้ามล้างตามอายุอย่างเดียว

### 9. เวลาถูกต้องเพราะ DB ตั้งเป็น UTC เท่านั้น
- **อาการ:** คอลัมน์ใช้ `DEFAULT timezone('utc'::text, now())` ซึ่งได้เวลา UTC แบบไม่มีโซน
  แล้วเก็บลง TIMESTAMPTZ ซึ่ง Postgres จะตีความตาม timezone ของ session
- **ผลกระทบ:** ถูกตอนนี้ (`SHOW timezone` = UTC) ถ้าวันไหนมีคนตั้ง timezone ของ DB เป็น
  Asia/Bangkok เวลาที่บันทึกใหม่ทั้งหมดจะเพี้ยนไป 7 ชั่วโมงโดยไม่มี error
- **วิธีแก้:** เปลี่ยน default เป็น `now()` เฉย ๆ (TIMESTAMPTZ เก็บเป็นจุดเวลาอยู่แล้ว)

## ข้อมูลส่วนบุคคลและการสำรองข้อมูล

### 10. ไม่มี backup อัตโนมัติ
- มีแค่ `pg_dump` ที่ทำด้วยมือก่อนแก้ schema ใน `backups/` (3 ไฟล์, 6.1 MB, gitignore แล้ว)
  อยู่เครื่องเดียวกับ DB และไม่เข้ารหัส ถ้าเครื่องเสียหายหายทั้งคู่
- `docker compose down -v` ลบ volume `pgdata` ทั้งหมดในคำสั่งเดียว
- **วิธีแก้:** backup ตามเวลาไปเก็บนอกเครื่องและเข้ารหัส (บน Supabase ใช้ backup ของแพลตฟอร์ม)

### 11. ลบผู้สมัครแล้วข้อมูลบางส่วนยังค้าง (PDPA)
- `email_intake_log` เก็บ `from_addr` กับ `subject` โดยไม่มี FK ไปผู้สมัคร (ไม่มี FK โดยตั้งใจ
  เพื่อให้ log อยู่รอด) แถวจึงไม่หายตามตอนลบผู้สมัคร
- ไฟล์ backup เก่ายังมีข้อมูลคนที่ถูกลบไปแล้ว
- **วิธีแก้:** ตอนลบผู้สมัคร ให้ลบหรือปิดบังแถว log ที่ `candidate_id` ตรงกัน · กำหนดอายุ backup

### 12. ข้อมูลทดสอบค้างอยู่
- 13 จาก 21 คนไม่มี `resume_sha256` (สร้างก่อนมีระบบกันซ้ำ) จึงกันอัปโหลดซ้ำไม่ได้
- ชื่อซ้ำในตำแหน่งเดียวกัน 4 กลุ่ม เช่น Jeerawat Sakwong 7 แถว (รวมแถว `a8ce77b3`
  ที่กราฟค้างกลางทาง ดู 02_progress.md)
- **วิธีแก้:** ล้างก่อนใช้งานจริง ใช้ปุ่มลบผู้สมัครเดิมเพื่อให้ checkpoint ถูกลบตามด้วย

## ที่ดีอยู่แล้ว — อย่าแก้จนพัง
- checkpoint กำพร้า 0 thread: การลบผู้สมัครเก็บกวาด checkpoint ครบ
- FK และ CASCADE ถูกต้อง · `employees` **ไม่** cascade โดยตั้งใจ (ระเบียนพนักงานต้องอยู่รอด)
- pgvector 0.8.5 พร้อม HNSW index
- SQL ทุกคำสั่งใช้พารามิเตอร์ ไม่มีการต่อข้อความเป็นคำสั่งเอง

## ลำดับที่แนะนำเมื่อจะแก้
1. RLS หรือปิด Data API (ถ้าไป Supabase) — ข้อ 1
2. checkpointer ต่อใหม่ได้ — ข้อ 2
3. index + UNIQUE ที่ `evaluations` และ index ที่ `processing_queue` (ล้างแถวซ้ำก่อน) — ข้อ 6, 7
4. เปลี่ยนรหัสผ่าน DB และตั้ง backup อัตโนมัตินอกเครื่อง — ข้อ 3, 10
5. นำเครื่องมือ migration มาใช้ก่อน schema เปลี่ยนครั้งถัดไป — ข้อ 5
