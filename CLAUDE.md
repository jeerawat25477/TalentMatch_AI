## What the system is meant to do

An HR resume-screening assistant. HR uploads a job description and a batch of PDF resumes; a multi-agent LangGraph pipeline parses both, scores each candidate against the JD, audits the scoring for bias, and then either drafts interview questions or a rejection email. Candidates in the ambiguous scoring band stop the graph and wait for a human decision.

## Architecture: the pieces only make sense together

**One graph, one state object.** `HRSystemState` (a `TypedDict`) is the single value threaded through every node, and nodes are pure state transformers. Keep it in `app/agents/state.py` as the one definition (`project_brief.md` and `backend_langgraph.md` both show it; they must not drift apart).

**Node order is fixed and each stage depends on the previous one's normalized output:** `jd_analyzer` → `resume_parser` → `retrieve_similar` → `matcher` → `bias_auditor` → conditional router (one edge goes back to `matcher` for the bias revise loop). `resume_parser` is a separate node because it must emit resumes in *the same JSON shape* as the JD analyzer's `JobRequirement`, so `matcher` can do a field-by-field gap analysis rather than free-text comparison.

**`retrieve_similar` is an optional RAG agent** (`app/agents/nodes/retriever.py`), toggled by `RAG_ENABLED`. When off it is a pure no-op — the node stays in the graph so the shape (and checkpointer) never changes; it just returns empty. When on it queries pgvector for past applicants with a similar skill profile (`vectors.search(..., exclude_candidate_id=cid)` so a re-indexed candidate can't match itself), stored on `evaluations.similar_candidates` and surfaced to the UI. It uses **embedding quota (separate from the daily chat quota, `GEMINI_DAILY_CHAT_QUOTA`)** and `interview_planner` folds the result into its existing prompt, so it adds **zero** chat calls. Scope: comparative context for the human + sharper interview questions — it does **not** change the deterministic fit score.

**Scoring is deterministic and lives in two files only:** skill comparison in `app/agents/skills.py`, the formula in `nodes/matcher.py::compute_fit_score` (required 60% / preferred 40%, renormalized over whichever sides the JD actually specifies). `matcher` must not compare skill strings itself and the LLM never writes a score. Any change here moves every candidate's score — follow the `scoring-change` skill.

**The router is the heart of the product.** After `bias_auditor`, `route_candidates` decides:
- **an HR decision on record wins over the score, always** — `approved` → advance, `rejected` → reject
- otherwise `> 70` → advance, and `runner` auto-resumes past the interrupt
- otherwise `50–70` → advance, but `runner` stops and waits for HR
- otherwise `< 50` → `email_drafter` (rejection)

**One critique/revise loop, capped at one round.** When the job's bias audit (`jobs.jd_audit`, read by the `bias_auditor` node) flags a run and names JD skill criteria to drop, the router returns `"revise"`, `matcher` removes them and recomputes deterministically, and the auditor checks again. The record of that pass is `evaluations.bias_revision` — without it the loop is invisible, since the second audit overwrites `audit_log`. Guards and costs are in the `graph-node` skill.

**`jd_analyzer` sanitizes the JD before the auditor ever sees it — proven with real Gemini (2026-09-01).** Its prompt admits only "things the candidate can do" into `required_skills`/`preferred_skills`, so "จบจากมหาวิทยาลัยชั้นนำ" lands in `education` and "เพศชาย อายุไม่เกิน 30 ปี" is dropped entirely. The skill-exclusion loop is therefore a second net, not the anti-bias mechanism. What works is auditing the **raw JD text** (truncated to `_MAX_JD_CHARS` for the LLM) plus `education`/`min_experience_years` for `biased_jd_criteria` — biased criteria that are *not* skills, so they can't be excluded from a score they never fed. They render as a "⚠ เกณฑ์ใน JD ที่อาจมีอคติ" line in `audit_log`.

**The bias audit is per job, not per candidate (since 2026-09-28).** Everything the auditor looks at belongs to the job; the only per-candidate input was the deterministic gap analysis, which cannot see gender or age. So `POST /jobs/analyze` runs `bias_auditor.audit_jd` **once** — sequentially after `extract_jd`, not in parallel, because it must see the extracted skill list to name biased skills — and `build_jd_audit` merges it with the fixed regex rules in `agents/bias_rules.py` (read the full JD, cost nothing, and override an LLM "passed" that contradicts them). HR sees the warning in the confirm step *before* saving; `create_job` recomputes the rules server-side from `raw_text` (the client only returns the LLM's raw result as `bias_llm`, like `extraction`) and stores `jobs.jd_audit`. The `bias_auditor` node stays in the graph but **never calls the LLM**: `queue_worker` loads `jobs.jd_audit` into `state["jd_audit"]`, and a missing value (old checkpoint, or a job created without the LLM) falls back to rules only. Every candidate in a job therefore gets the identical audit text. Old jobs were backfilled rules-only with `scripts/backfill_jd_audit.py` (`--with-llm` costs 1 call per job). HR can mark a flagged phrase as genuinely required for the job ("เพศหญิง" for a body-search officer) — per phrase, with a reason of at least 10 characters, attributed to the logged-in user — in `jobs.bias_acknowledgements`, kept separate from `jd_audit` because one is the machine's output and the other a human decision (`app/bias_ack.py`, `PUT /jobs/{id}/bias-acknowledgements`). The candidate page reads the job's audit + acknowledgements live (`CandidateDetail.job_bias`) instead of the evaluation's `audit_log`, so a later acknowledgement reaches existing candidates without rewriting their screening record. Acknowledging a JD phrase never touches the score. Skills the LLM itself named as biased (`jd_audit.biased_*_skills`) follow the same acknowledge-or-remove rule since 2026-10-14, and for them acknowledging **does** move scores: `bias_ack.effective_biased_skills` (still in the criteria by `canonical`, not acknowledged) is the one list of what the revise loop must exclude — `queue_worker` passes `audit_for_graph` into state (state shape and the `bias_auditor` node unchanged), the criteria editor's `rescore_job` uses it instead of each evaluation's old `bias_revision`, and `PUT /bias-acknowledgements` rescores existing candidates in the same transaction when it changes (preview at `POST .../bias-acknowledgements/preview`). Removing such a skill in the criteria editor clears its warning. The one gate on HR-typed criteria is `bias_ack.biased_skills` (rules only, no LLM): the AI audits the skill list only at `/jobs/analyze`, so a skill HR types in afterwards — in the confirm step or the later criteria editor — that matches a flagged JD phrase (e.g. "Native English speaker") or itself trips `bias_rules` makes `create_job` / `PUT /jobs/{id}/criteria` return 409 `detail.code = "biased_skill"` until HR removes it or acknowledges that phrase (an acknowledged phrase may then be scored); preview lists it as a warning instead. Matching deliberately ignores short real skills inside a flagged phrase ("English", "ภาษาอังกฤษ") — checked against all 199 skills of the 16 dev jobs with zero hits. The reverse door is closed too: `PUT /jobs/{id}/bias-acknowledgements` refuses (409 `biased_skill`, `bias_ack.withdraw_blocked`) to withdraw an acknowledgement while that phrase is still a scoring skill, and `bias_view` marks such acknowledgements `scored` so the UI can say the phrase counts toward the score.

**Every threshold lives in `app/agents/bands.py`.** Never write `50` or `70` anywhere else — they were previously duplicated across the router, runner, drafter, matcher, a script, and the frontend, so moving a boundary silently desynced the badge colors from the path the graph actually took. `frontend/lib/types.ts::scoreBand` is the one unavoidable copy; change both together.

**Human-in-the-Loop: resume when paused, rewind when finished.** The graph is compiled with a checkpointer and `interrupt_before=["interview_planner"]`. `runner.resume_after_decision` must keep handling both cases — paused at the interrupt, and already finished (which needs `update_state(..., as_node="bias_auditor")` to rewind so the router re-decides). Without the rewind branch HR could never overturn an automatic decision, and `<50` candidates were unrescuable by construction. In neither case may the graph re-run from the entry point: that re-bills every LLM call and loses context. `CandidateDetail.graph_status` tells the UI which case it is; the mechanics are in the `graph-node` skill.

**Checkpointer storage matters.** `backend_langgraph.md` shows `SqliteSaver.from_conn_string(":memory:")`, which is illustrative only — in-memory state dies on restart and breaks HITL. `database_supabase.md` supersedes it: use `PostgresSaver` from `langgraph-checkpoint-postgres` against the Supabase connection string, and call `saver.setup()` once to create the checkpoint tables.

**Deleting a candidate is the narrow-scope sibling of deleting a job.** `DELETE /api/v1/candidates/{id}` exists for the wrong-file / duplicate-upload case — cascade touches only that person's `evaluations`, `hr_decisions`, and `resume_embeddings`. `candidates.py::_candidate_deletion_blocker` applies the same two rules as jobs (409 if an email was sent to them, 409 if the graph is running), and checkpoint cleanup is the same `delete_thread`-after-commit ordering. **Upload dedupes on content, per job.** `candidates.resume_sha256` plus a `UNIQUE (job_id, resume_sha256)` index means the same PDF re-uploaded is skipped, not re-run — the response carries `skipped`/`duplicate_files` and the UI names the files it dropped. The key is the sha256 of the bytes, deliberately *not* the filename (renaming would defeat it) and not the parsed email (not known at upload time, and it comes from an attacker-controllable PDF). Alongside it, `_is_unreadable_resume` rejects a file whose extracted text is under `MIN_RESUME_TEXT_CHARS` (default 80 non-whitespace chars) — a scanned or photographed resume has no text layer, and without this guard the upload created a candidate with empty text and spent ~3 chat calls having the LLM analyze nothing, while the API reported success. `reprocess` calls the same function so the two entry points cannot disagree. It answers "is there enough text", not "is this really a resume" — a scan with a stray text box still gets through; only OCR would close that. `candidates.py::_is_duplicate_upload` is a pure function so it stays unit-testable; the INSERT additionally uses `ON CONFLICT … DO NOTHING` so two concurrent uploads of one file can't both win — never swap that for a caught `UniqueViolation`, since the aborted statement would poison the whole batch's transaction. Two limits remain: rows created before this column exists have `resume_sha256 = NULL` and cannot be backfilled (the bytes were never stored), and NULLs never collide in Postgres, so an old row will not block a re-upload; and dedupe only closes the *source* of double-emailing — `email_sent_at` still lives on `evaluations`, so it is per-row, not per-person.

**Applications can also arrive by email, and that path is off until someone turns it on.** `app/email_intake.py` polls an IMAP mailbox, matches each message to a job by `apply+<job_id>@` in Delivered-To/To/Cc (or `[job:<uuid>]` in the subject), and feeds accepted attachments through the same admission gate and the same `processing_queue` as a manual upload — so quota throttling, `deferred_quota`, and one-at-a-time execution all apply unchanged. Four rules hold it in place. **It defaults to off and sleeps completely when off**: the switch lives in `app_settings` (read through `app/settings.py`'s 10-second cache so HR can flip it without a restart), and a disabled tick opens no socket at all — the same no-op discipline as `RAG_ENABLED`. **It never guesses a job with an LLM**: an unmatched message is left in the mailbox and logged, because guessing costs from the same daily chat budget and a wrong guess files someone under the wrong role. **It is read-only by construction**, not by intention: `select(readonly=True)` plus `BODY.PEEK[]` rather than `BODY[]`, which would set `\Seen` and disturb a mailbox HR still reads themselves. And **it only ever receives** — nothing in that module imports `email_sender`, because a reply to a candidate still requires HR to press send (see "Email send is synchronous and HR-gated"). HR flips the switch on the settings page, and each job's detail page shows the exact address to advertise, copy button included — both derived from `apply_address_template()`, which builds it from `IMAP_USER`. That one source matters: the address matcher accepts **any** local part before the `+`, not the literal string `apply`, because it once hardcoded `apply+` while the page advertised `recruit+…` from a differently-named mailbox, and every application sent to the address the product itself printed came back `unmatched`. A test now pins the two together — whatever `apply_address_template()` produces must be matched by `extract_job_id()`.

Two IMAP details are easy to get wrong and both are load-bearing. A UID means nothing without its mailbox's `UIDVALIDITY`, so both are stored together and a change resets the cursor — without that check a recreated mailbox either silently skips every new message or re-ingests the whole box. And `UID n:*` always returns the newest message even when nothing is new, so the code filters `uid >= start` again itself; skip that and every poll reprocesses the same message forever. `last_uid_seen` advances **per message**, not per batch, so a worker that dies mid-run resumes instead of repeating work already paid for. Every message lands in `email_intake_log` whatever happens to it — that table is what makes "matched 3, couldn't place 2" answerable for HR without reading container logs, and it survives restarts in a way an in-process counter would not.

**Resume admission lives in `app/resume_ingest.py`, shared by both entrances.** Magic byte, size cap, sha256 dedupe, text-extraction, the unreadable check, and the `ON CONFLICT DO NOTHING` insert are one sequence called by both `upload_resumes` and the email worker. It returns a `Verdict` rather than raising, so the router can map it to 400/413 and the worker can map it to a log row; a second copy of these rules is exactly the drift `bands.py` and `compute_fit_score` exist to prevent.

**Job lifecycle: close, don't delete.** `jobs.status` is `open | closed`; `PATCH /api/v1/jobs/{id}` flips it and `upload_resumes` returns 409 on a closed job. Closing is the intended move when a role is filled, because `candidates.job_id` cascades all the way to `evaluations`, `hr_decisions`, and `resume_embeddings` — deleting a job shrinks the RAG corpus `retrieve_similar` depends on and destroys the `email_sent_at`/`email_sent_to` audit trail. `DELETE /api/v1/jobs/{id}` exists for jobs created by mistake and is guarded by `jobs.py::_deletion_blocker`: it refuses (409) if any email was already sent, or if the graph is mid-run for one of the job's candidates (`runner.active_candidates()`, an in-process set — same single-replica caveat as the login rate limiter). Checkpoint rows have no FK to `candidates`, so `delete_job` collects `candidate_id`s *before* the cascade and calls `PostgresSaver.delete_thread` per thread **after** the DB commit — that order is deliberate: a failure there leaves harmless orphans, whereas the reverse would wreck the HITL state of a job that still exists.

**Resume upload is asynchronous, through a durable queue.** `POST /api/v1/jobs/{job_id}/resumes` extracts text, writes candidate rows immediately, then inserts one `processing_queue` row per candidate and returns 202. The frontend polls the candidate list; it does not wait on the graph. Every other background job goes the same way — `reprocess`, `submit_decision`, and bulk decisions all just enqueue.

**Text extraction is PyMuPDF, and that choice is about Thai.** Thai stacks vowels and tone marks above the consonant, and design tools (Canva et al.) emit those glyphs into the content stream *after* the following consonant — so ordering by x coordinate (`pdfplumber`) and reading the stream in order (`pypdfium2`) are **both wrong**. Measured on two real Thai résumés: pdfplumber gave `จรี วฒั น์ ศักดิ วงษ์` / `มหาวทิ ยาลัย`; pypdfium2 was *worse*, shredding one file into 300+ single-character lines; PyMuPDF gave `จีรวัฒน์` / `มหาวิทยาลัยมหาสารคาม` / `รับผิดชอบ` correctly, because it reorders Thai combining marks itself. Latin is unaffected by any of this, which is why scores never looked wrong while names did. Do not "simplify" back to a permissive-license engine without re-running that comparison — the obvious candidates were tried and failed.

⚠ **PyMuPDF is AGPL-3.0** (the user chose this knowingly): serving this app to third parties over a network obliges you to publish the whole system's source. `pdfplumber` (MIT) stays as the fallback path in `utils/pdf_extractor.py`, which also caps pages at `MAX_PDF_PAGES` (decompression bombs) and must keep stripping both `\x00` (Postgres `text` rejects NUL) and `\r`. A regression test for the Thai bug does **not** exist: a reportlab-generated Thai PDF lays each line down as one string and even pdfplumber reads it correctly, so it cannot reproduce the bug — only real-world PDFs that place glyphs individually do. Residual known defect: résumés embedding a font with a broken ToUnicode table yield stray Latin letters for some marks (`เปqน`, `แก้ปaญหา`) — a file defect, not an engine one.

**Work lives in `processing_queue`, not in the process.** `BackgroundTasks` was in-process: a container restart, hot-reload, or an exhausted Gemini quota left a candidate row with no `evaluations` row and nothing that would ever finish it, while the UI's `pending` band rendered that as "กำลังวิเคราะห์…" forever. Every background job is now a row in `processing_queue` (`kind` = `process` | `reprocess` | `resume_after_decision`), and a single daemon thread (`app/queue_worker.py`, started from `main.py`'s lifespan) claims the oldest one at a time with `FOR UPDATE SKIP LOCKED`. Two rules make the durability real and must both stay: `main.py` calls `job_queue.reclaim_running()` **before** starting the worker, which flips rows left in `running` back to `queued` (nothing is genuinely running at boot, so such rows are always debris from a dead process); and the worker calls the existing `runner.process_candidate` / `runner.decide_candidate` rather than reimplementing the walk, which is what keeps the HITL invariant intact — measured 2026-09-10, approving a finished candidate cost exactly +2 chat calls and left `evaluations.created_at` untouched, i.e. a resume, not a rerun.

**Quota is a scheduling input, not an error.** `app/llm_quota.py` counts every successful call at the one place they all pass through, `agents/llm.py::structured_invoke_once` (`structured_invoke` merely wraps it), into `llm_quota_usage` keyed by model and by **Google's own quota day, midnight Pacific** (`GEMINI_QUOTA_TZ`) — best-effort, wrapped in try/except, because a counter must never break a call. The worker checks `GEMINI_DAILY_CHAT_QUOTA` (code default 20 = the free-tier cap; this deployment sets 500 since billing was enabled 2026-09-19) against `job_queue.COST_BY_KIND` **before** claiming work and parks the job as `deferred_quota` when there isn't room. `deferred_quota` is a **pause, not a terminus**: `claim_next` picks such rows up again after `QUEUE_DEFERRED_RETRY_SEC`, so a job never needs the reset to be timed correctly to eventually run. The day boundary was UTC at first, on the unchecked assumption that `python:3.12-slim` lacks a timezone database — it ships `/usr/share/zoneinfo`, and UTC named the wrong day 30.6% of the year, a gap that lands squarely on the Thai working morning: calls made then are billed to Google's *previous* day but counted against *ours*, so the afternoon parks work while the real quota sits empty. `quota_date(now, tz)` is pure so every boundary case is testable without mocking the clock, and it falls back to a fixed eight-hour offset if the zone can't be read — eight, not seven, because that offset is never *ahead* of real Pacific (verified across 2026–2027), so it can only over-defer, never blunder into a 429. That Google resets at midnight Pacific remains documented behaviour we have not measured here; `GEMINI_QUOTA_TZ=UTC` reverts the whole thing without a code change. `job_queue.classify_failure` must keep quota errors out of the `temporary` bucket — counted as retries they would burn `attempts` and land as `failed` a job that would run fine tomorrow. `COST_BY_KIND` says 4 for `process`: `resume_parser` makes two calls since phase 1, plus planner and drafter. It was measured at 5 (2026-09-10) when `bias_auditor` still called the LLM per candidate; the audit moved to job creation on 2026-09-28, so 4 is that measurement minus the removed call — re-measured 2026-10-12 with `scripts/eval_resumes.py`: exactly 4 on the advance path, 3 on the reject path (results in `memory-bank/06_scoring_criteria.md`). `/jobs/analyze` now costs 2 (`ANALYZE_COST`). The "~3 per candidate" in older notes predates the parser's second call.

**The stalled badge and the queue answer different questions.** `candidates.py::_is_stalled` (no evaluation + not in `runner.active_candidates()` + **no pending queue row** + older than `STALLED_AFTER_SEC`, default 90) still drives the "วิเคราะห์ไม่สำเร็จ" badge and `POST /api/v1/candidates/{id}/reprocess`, which re-enqueues from the `raw_resume_text` already in the DB — no re-upload. It refuses (409) if an evaluation already exists (a rerun would burn quota and could overwrite an HR decision), if the candidate is already active, or if a queue row is already pending. The queue-row check is not redundant with the registry: `_active` is in-process and empty after a restart, while the queue row survives — without it every queued candidate would look dead the moment the container restarted. `queue_status` is surfaced on `CandidateSummary`/`CandidateDetail` so the UI can say "รอคิวประมวลผล" or "เลื่อนไปวันถัดไป" instead of implying a failure. Uploads still `reserve_candidates` the **whole batch** up front, because the registry also drives the delete guard.

## Stack and conventions

- **Backend:** Python 3.10+, FastAPI + Uvicorn, LangGraph/LangChain, `langchain-google-genai`. The briefs say Gemini 1.5 Flash/Pro, but **1.5 is retired (404 NOT_FOUND)**. `app/agents/llm.py` defaults both tiers to `gemini-2.5-flash`, overridable via `GEMINI_DEFAULT_MODEL` / `GEMINI_COMPLEX_MODEL`. **Billing is enabled (Tier 1, prepaid, 2026-09-19)**: 2.5-flash 1K RPM / 10K RPD, 2.5-pro 150 RPM / 1K RPD, 2.5-flash-lite 4K RPM / unlimited RPD — so Pro is now usable (on the free tier it returned 429 `limit: 0`); set `GEMINI_COMPLEX_MODEL=gemini-2.5-pro` to restore the Flash/Pro split. The deployed `.env` runs `gemini-2.5-flash` for both with `GEMINI_DAILY_CHAT_QUOTA=500`. The account is prepaid with auto-reload off, so the daily cap is now a spend guard, not a Google limit — raising it spends money. Measurements recorded before 2026-09-19 (e.g. jd_analyzer label accuracy) were taken on `gemini-2.5-flash-lite`.
- **Structured output:** every LLM-producing node defines a Pydantic v2 model for its output (e.g. `JobRequirement`) rather than parsing free text.
- **Persistence:** Supabase Postgres. Four app tables — `jobs`, `candidates`, `evaluations`, `hr_decisions` — plus LangGraph's own checkpoint tables. DDL lives in `database_supabase.md`; `hr_decisions.candidate_id` is `UNIQUE` (one decision per candidate).
- **Vectors:** **pgvector** (the `db` service uses `pgvector/pgvector:pg16`), table `resume_embeddings` with an HNSW cosine index; code in `app/vectors.py`, exposed as `GET /api/v1/candidates/search`. Embeddings are `models/gemini-embedding-001` truncated to 768 dims via `output_dimensionality` — the `VECTOR(768)` column and `EMBEDDING_DIM` must stay in sync. (The briefs say `models/text-embedding-004`; that model is no longer callable — it is absent from ListModels.)
  - **Scope: ranking for a human, never a matching decision.** Measured cosine on this model puts PostgreSQL↔MySQL at 0.885 and Java↔JavaScript at 0.865, *above* a pair that should match (React Native↔Mobile Hybrid, 0.838) — so no threshold separates them. Skill matching is deterministic in `app/agents/skills.py`; do not replace it with similarity.
- **Frontend:** Next.js App Router + TypeScript. The design system is **"Luminous HR"** and `frontend/DESIGN.md` is its source of truth: a light-first glassmorphism theme on Material 3 token families, primary Trustworthy Blue `#0058be`, with a Navy dark counterpart selected by `.dark` on `<html>`. Every token is a CSS variable in `app/globals.css` and is consumed through Tailwind — never hardcode a hex in a component. Score bands own the only saturated non-blue colors in the app (`--band-pass` emerald, `--band-review` amber, `--band-fail` red), so nothing decorative may borrow them. Backend is published on host port **8080** (container still listens on 8000; host 8000 falls in WinNAT's reserved 7909–8008 range and can't bind — same Windows issue as 3000→4000), frontend at `:4000`; the browser calls the backend via `NEXT_PUBLIC_API_BASE_URL=http://localhost:8080`. CORS must allow the frontend origin explicitly.
- **LangGraph Studio (dev only):** `docker compose --profile studio up -d studio` serves `app/agents/studio.py` (the real `build_graph()` + the same interrupt, no PostgresSaver) on `127.0.0.1:2024`; `scripts/studio_input.py <candidate_id>` prints a real candidate's initial state via `runner.initial_state`. Running it in Studio spends real Gemini calls but never writes to the HR tables. How-to in `memory-bank/03_environment.md`.
- **Tracing:** LangSmith is wired. It is env-driven, not a code toggle — LangChain/LangGraph auto-instrument when `LANGCHAIN_TRACING_V2=true` and `LANGCHAIN_API_KEY` are set (SDK also honors `LANGSMITH_*`); absent those, callbacks no-op with zero overhead. `runner._config` labels each graph run (`run_name=screen-candidate-<id8>`, `tags=["talentmatch","screening"]`, `metadata.candidate_id`) so a candidate's trace is findable in the LangSmith UI. `app/tracing.py::tracing_status` logs on/off at startup. Any new graph invocation should pass a config built the same way so its trace is labeled too. **pytest never traces**: `tests/conftest.py` forces `LANGCHAIN_TRACING_V2`/`LANGSMITH_TRACING` to false and clears the SDK's env cache (pinned by `tests/test_tracing_off.py`) — before that, test runs were ~80% of the project's traces and their simulated 429s showed up as a 16% error rate, while the 62 real-Gemini traces had 0 errors (checked 2026-10-12). Scripts under `scripts/` run outside pytest and still trace.

## Secrets

`.env` in `backend/` holds the Gemini API key, Supabase connection string, LangSmith key, and (for prod) SMTP credentials. Nothing runs without them; `.env.example` documents every variable — keep it in sync when adding code that reads a new one. A root `.gitignore` now excludes `.env` (the repo is not yet a git repo, but the guard is in place before the first commit).

**Auth gates every endpoint except `/health` and `/api/v1/auth/login`.** JWT (HS256) with `app/auth.py::get_current_user` applied as a router-level dependency on jobs/candidates/hr — add the same dependency to any new router. `JWT_SECRET` has no hardcoded default on purpose (a shared default = anyone can forge tokens); the app refuses to sign/verify without it. The initial user is seeded from `ADMIN_USERNAME`/`ADMIN_PASSWORD` in `init_db()` (idempotent). **Two roles since 2026-10-16** (`users.role`): `admin` does everything; `demo` is a tester account for the professor/friends — everything HR does except delete and change settings. `auth.require_admin` guards exactly those 5 endpoints (email send was guarded at first, then opened to demo the same day by the user's choice so the professor can test like real HR — `send_candidate_email` now logs `<user> ส่งอีเมลถึง <to>` on every send, because the first incident could not tell who pressed send), reading the role from the DB on every request (`get_current_role`, never from the token) so a role change or `remove` takes effect at once. `tests/test_roles.py` walks every route and fails if a new `DELETE` lacks the guard (only deleting HR's own email-draft edit is exempt) or if the guarded set drifts from the plan. The column defaults to `demo` for new rows (least privilege; existing rows were filled `admin`), and `tests/conftest.py` defaults the role override to `admin` because older tests stub `get_current_user` with names that have no `users` row. Accounts are made with `scripts/manage_users.py` on the server (no user-management UI); the frontend hides the matching buttons via `lib/use-me.ts::useIsAdmin` for convenience only. Login is rate-limited in memory per IP+username (5 fails / 5 min → 429) — swap for Redis before running more than one backend replica. Frontend stores the Bearer token in `localStorage` and `lib/api.ts::request` attaches it and redirects to `/login` on any 401; `AppShell` guards routes and hides its chrome on `/login`.

**Email send is synchronous and HR-gated.** `POST /api/v1/candidates/{id}/email/send` takes the recipient/subject/body that HR sees and confirms on screen — never the LLM-parsed `candidate.email` directly, because that address comes from an uploaded PDF and sending to it blindly would make the app a spam relay. `app/email_sender.py` uses `email.message.EmailMessage` (header-injection safe) plus a CRLF sanitizer. The same endpoint scans subject + body with `bias_rules.find_biased_message_phrases` before sending and returns 409 (`detail.code = "bias_warning"`, with the phrases) unless `acknowledged_bias_warning` is true — built into the send endpoint rather than a separate check so the frontend cannot skip it; sending anyway is logged with the user. The AI drafts never see the résumé (the planner gets job title and skill gaps, the drafter only name and title), so the realistic source of such wording is HR's own edits and templates; `tests/test_prompt_privacy.py` pins that data minimisation. Dev sends to MailHog (`mailhog:1025`, UI at :8025); prod overrides `SMTP_*` env for real SMTP. `EMAIL_TRANSPORT=gmail_api` sends the same `EmailMessage` through the Gmail API over HTTPS instead (stdlib `urllib`, scope `gmail.send` only, a fresh access token per send, no cache) — added 2026-10-15 because DigitalOcean blocks outbound 25/465/587 on new accounts; `scripts/gmail_oauth_setup.py` writes `GMAIL_*` into `backend/.env` on the server. A revoked/expired grant (`invalid_grant`, e.g. the Google Cloud app left in Testing = 7-day tokens) raises `EmailConfigError` → 503, not 502, because retrying cannot fix it. Never log the token or secret. `PRIVACY.md` (the public policy the Google consent screen links to) lists every place data leaves the system — Gemini, Gmail, DigitalOcean; adding a new one (turning on LangSmith in prod, an email relay, OCR) means updating it in the same change. Uploads are size/count-capped and magic-byte-checked in `candidates.py`.
