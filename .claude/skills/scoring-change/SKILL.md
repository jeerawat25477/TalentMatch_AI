# แก้ตรรกะการให้คะแนน

การแก้ที่นี่ทำให้คะแนนของผู้สมัคร **ทุกคน** เปลี่ยน รวมถึงคนที่ HR ตัดสินไปแล้ว จึงคุ้มที่จะทำตามลำดับด้านล่างแม้การแก้จะดูเล็กแค่ไหน

เส้นทางไฟล์ทั้งหมดในเอกสารนี้นับจากรากของ repo ส่วนคำสั่งที่รันในคอนเทนเนอร์ใช้เส้นทางของคอนเทนเนอร์ ซึ่งมี `backend/` เป็นรากอยู่แล้ว

## ลำดับงาน

1. **เขียนเทสก่อนแก้โค้ด** เพิ่มเคสใน `backend/tests/test_skills.py` (การเทียบทักษะ) หรือ `backend/tests/test_scoring.py` (สูตรคะแนน) ให้มันแดงก่อน เพราะเคสที่เพิ่งพังคือหลักฐานชิ้นเดียวที่บอกได้ว่าแก้แล้วตรงจุด
2. แก้โค้ดในไฟล์เดียวที่รับผิดชอบเรื่องนั้น (ดูตารางด้านล่าง)
3. รันเทสทั้งชุด: `docker compose exec -T backend python -m pytest tests/ -q`
4. ถ้าสูตรหรือการเทียบเปลี่ยน ให้ดูผลกับข้อมูลจริงก่อนด้วย `docker compose exec -T backend python scripts/recompute_scores.py` แบบ dry-run แล้วค่อยใส่ `--apply`
5. อัปเดต `memory-bank/02_progress.md` ถ้าเป็นการเปลี่ยนเชิงพฤติกรรม

## ใครรับผิดชอบอะไร

| เรื่อง | ไฟล์เดียวที่ควรแก้ |
| --- | --- |
| ทักษะ A ถือว่าตรงกับ B ไหม | `backend/app/agents/skills.py` |
| สูตรคะแนน 0-100 | `backend/app/agents/nodes/matcher.py::compute_fit_score` |
| เส้นแบ่ง pass/review/fail และ confidence | `backend/app/agents/bands.py` |
| ข้อความอธิบายคะแนน | `backend/app/agents/explain.py` |

## สิ่งที่เคยพังมาแล้ว และเหตุผลที่โค้ดเป็นแบบนี้

**การเทียบทักษะทำบนขอบเขตคำ ไม่ใช่ substring** โค้ดรุ่นแรกใช้ `n in o or o in n` ผลคือ required `R` ถูกนับว่าตรงกับ `docker` `redis` และ `postgresql` ส่วน `ML` ตรงกับ `html` ตรรกะการเทียบอยู่ใน `matching_owned` ที่เดียว ส่วน `matches` เรียกต่อจากมัน ถ้าเขียนการเทียบซ้ำที่สอง สองสำเนาจะค่อย ๆ ต่างกันจนคะแนนกับหลักฐานที่แสดงให้ HR ไม่ตรงกัน

**`IMPLIES` เป็นความสัมพันธ์ทางเดียว** รู้ PostgreSQL ย่อมเขียน SQL ได้ แต่รู้ SQL ไม่ได้แปลว่าใช้ PostgreSQL เป็น `_covers` ก็ยึดหลักเดียวกัน required `SQL` ผ่านด้วย owned `SQL Server` แต่ required `React Native` ไม่ผ่านด้วย owned `React` การทำให้เป็นสองทางเพื่อความสะดวกจะแจกคะแนนให้คนที่ยังทำงานนั้นไม่ได้

**เรียก `canonical()` ก่อน tokenize เสมอ** ถ้าสลับลำดับ `NodeJs` ซึ่งเป็น 1 token จะไม่มีวันตรงกับ `Node.js` ซึ่งเป็น 2 token

**เลข 50 และ 70 อยู่ใน `backend/app/agents/bands.py` ที่เดียว** ก่อนหน้านี้มันกระจายอยู่ใน router, runner, drafter, matcher และสคริปต์ พอย้ายเส้นแบ่งแล้วแก้ไม่ครบ สีป้ายในเว็บกับเส้นทางที่กราฟเดินจริงก็ไม่ตรงกันโดยไม่มีใครรู้ สำเนาเดียวที่เลี่ยงไม่ได้คือ `frontend/lib/types.ts::scoreBand` เพราะอยู่คนละ runtime แก้คู่กันในคอมมิตเดียว

**ฝั่งที่ JD ไม่ได้ระบุต้องไม่ถูกนับว่าผ่าน** ต้องเฉลี่ยน้ำหนักใหม่ให้ฝั่งที่ระบุจริงเป็น 100% เดิมฝั่งที่ว่างถูกนับเป็นผ่านเต็ม ทุกคนจึงได้ฟรี 40 คะแนน คนที่ตรงเกณฑ์ 0 จาก 19 ข้อยังได้ 40% ซึ่งไม่มีคำอธิบายใดทำให้ HR ยอมรับได้ กรณีที่ว่างทั้งสองฝั่งเท่านั้นที่ตกไปใช้ `REVIEW_FROM`

**สูตรคะแนนอยู่ใน `compute_fit_score` ที่เดียว** `backend/scripts/recompute_scores.py` เคยคัดลอกสูตรไปไว้เองแล้วหลุดไม่ตรงกัน ถ้ารันช่วงนั้นมันจะเอาบั๊กเก่ากลับมาทับคะแนนที่ถูกต้องไปแล้ว

**LLM ไม่เคยเป็นคนให้คะแนน** `matcher` คำนวณแบบ deterministic ล้วน แม้ในรอบ revise หลัง bias auditor ก็แค่ตัดเกณฑ์ที่ถูก flag ออกแล้วคำนวณใหม่ด้วยสูตรเดิม จุดนี้คือเหตุผลที่คะแนนอธิบายซ้ำได้และตรวจสอบย้อนหลังได้

**อย่าเปลี่ยนไปใช้ embeddings แทนการเทียบทักษะ** วัด cosine ของ `gemini-embedding-001` แล้ว PostgreSQL กับ MySQL ได้ 0.885 และ Java กับ JavaScript ได้ 0.865 ซึ่งสูงกว่าคู่ที่ควรตรงจริงอย่าง React Native กับ Mobile Hybrid ที่ 0.838 จึงไม่มี threshold ใดแยกสองกลุ่มนี้ออกจากกันได้

**`is_skill()` ตัดทิ้งเฉพาะเมื่อคำสุดท้ายเป็นชื่อบทบาท** เช่น `product owners` หรือ `data scientists` แต่ไม่ตัด `developer tools` เพราะคำบทบาทเป็นคำขยาย ของพวกนี้ถ้าหลุดเข้ามาจะไปเป็นตัวหารของสูตรแล้วกดคะแนนทุกคนลงพร้อมกัน

**`matching_owned` วนบน `sorted()` ไม่ใช่ `set`** ลำดับของ set ไม่คงที่ ผลคือหลักฐานที่ HR เห็นจะสลับไปมาระหว่างการรีเฟรชทั้งที่คะแนนเท่าเดิม ซึ่งบั่นทอนความเชื่อถือมากกว่าที่คิด

## ผลกระทบที่ควรเช็คก่อนปิดงาน

- เปลี่ยนเส้นแบ่งเท่ากับเปลี่ยนเส้นทางที่กราฟเดิน (ผ่านอัตโนมัติ รอ HR หรือร่างอีเมลปฏิเสธ) ดู `backend/app/agents/graph.py::route_candidates`
- `gap_analysis` ต้องคงการสะกดตามต้นฉบับ JD เพราะถูกส่งต่อให้ planner และ drafter เขียนเป็นภาษาคน และแสดงบน radar chart
- `skill_evidence` ผูกกับการสะกดในเรซูเม่ ส่วน `gaps` ผูกกับการสะกดใน JD การจับคู่สองฝั่งต้องผ่าน `matching_owned` ไม่ใช่เทียบสตริงเอง
